Case-study diagram kit

A throwaway prototype for one decision: how the portfolio's case-study pages draw architecture diagrams. Charting already settled the shape — inline SVG, the site's own theme tokens, no runtime dependency. This page makes it concrete and tests it against the one hard case: the same diagram has to read cleanly in both light and dark. Every diagram below is the real IIoT Trace architecture, from the research dossier.

Two candidate styles — Blueprint (hairline) vs. Filled (weighted)  ·  Rendered: forced light + forced dark, side by side, independent of your theme  ·  Toggle this page:

01 The primitives

Four building blocks cover every diagram the four case studies need: a node (a service or component), a tier band (a deployment / responsibility boundary), a labelled edge (who talks to whom, over what), and an accent edge (the one relationship the diagram exists to make a point about). A legend only appears when an encoding repeats.

02 Style A — Blueprint

Hairline borders, no fills, orthogonal connectors, edge labels sitting directly on the line. Closest to the site's terminal feel and to the ASCII diagrams in the project READMEs. The risk: on a bright ground, 1px lines can feel thin and the diagram can wash out.

03 Style B — Filled

Tier bands get a faint accent-tinted wash, nodes get a solid surface fill, edges are a touch heavier with solid arrowheads, and edge labels sit in a chip so they never collide with a line. More robust in light mode; slightly less "raw terminal".

05 How a diagram is authored

Every diagram above was rendered by the same ~90-line function from a plain object in the case study's data file. Positions are hand-placed on a 4px grid — four diagrams don't justify an auto-layout engine, and hand placement stays predictable and reviewable in a diff. 

// app/projects/_data/industrial-iot-platform.ts
architecture: {
  diagram: {
    viewBox: [0, 0, 680, 132],
    tiers: [
      { label: "edge tier — not containerised", accent: "orange", x: 0,   w: 210 },
      { label: "platform tier — docker",        accent: "cyan",   x: 224, w: 232 },
      { label: "business tier — docker",        accent: "purple", x: 470, w: 210 },
    ],
    nodes: [
      { id: "core",   x: 24,  y: 40, w: 160, h: 40, label: ["M5Stack CoreS3", "ESP32-S3"] },
      { id: "pipe",   x: 250, y: 40, w: 150, h: 40, label: ["data-pipeline", "Node.js"] },
      { id: "influx", x: 250, y: 92, w: 150, h: 32, label: ["InfluxDB 2.8"] },
      /* … */
    ],
    edges: [
      { from: "core", to: "pipe", label: "MQTTS · telemetry · QoS 0" },
      { from: "pipe", to: "influx", label: "sole writer", accent: true },
    ],
  },
  ascii: `  [Sensor] --RS-485--> [CoreS3] --MQTT--> [pipeline] --> [InfluxDB]  `,
},
  • One renderer, <CaseArchitecture>, lives in the template. It reads --d-* CSS variables that globals.css maps to the site's existing per-theme tokens — so light mode is handled by the palette the site already ships, not by anything diagram-specific.
  • The spec is the diff. A reviewer sees exactly what changed in a data file, not opaque SVG path data.
  • ASCII fallback is a sibling ascii string, rendered in a <pre>. Use it when the diagram is genuinely trivial (a 3-box line) or as the small-screen substitute below a breakpoint — never as the primary for a real architecture.
  • Small screens: the SVG sits in an overflow-x: auto container and scrolls; it never reflows. Below ~560px the caption offers "view as text" → the ASCII string.

The call I'm recommending: Style B (Filled), authored from the declarative spec above.

Blueprint is prettier in dark and truer to the terminal aesthetic, but it's exactly the style that wilts on the light ground — and light mode is a first-class theme here, not an afterthought. Filled keeps the mono type, the sharp corners and the accent language, holds up in both themes, and still reads as "this person's site", not a Lucidchart export. The accent-edge convention (one coloured, labelled relationship per diagram) is what keeps each figure making a single point instead of inventorying the system.

What I need from you: pick a style, and say whether the declarative-spec approach is fine or you'd rather just write JSX per diagram.
